# T-05: Ocenianie (przydział, recenzje, konsensus, moderacja)

## Kontekst
Repo `backend/`. Istnieją `apps.accounts`, `apps.competitions`, `apps.submissions`. Referencja: `docs/PROJEKT.md` 2.2 (Review, FinalGrade) i 2.4 (maszyna stanów). Skala punktów: `stage.scoringscale.allowed_values()`.

## Zakres
Nowa aplikacja `apps.grading`:
- `Review`: `submission` FK, `reviewer` FK CommitteeMember, `round` (1 = ślepa, 2 = rozjemcza), `score` (null do czasu SUBMITTED), `comment_internal`, `comment_for_participant`, `annotations` JSON (lista {page:int, rect:[x,y,w,h], text:str, public:bool}), `status` ASSIGNED/DRAFT/SUBMITTED, `submitted_at`. `unique_together (submission, reviewer, round)`.
- `FinalGrade`: OneToOne Submission, `score`, `method` CONSENSUS/THIRD_REVIEW/MODERATION/APPEAL, `decided_by` User, `decided_at`, `rationale`.
- `AuditLog` w `apps.core` (jeśli jeszcze nie ma): `actor`, `action`, `target_type`, `target_id`, `diff` JSON, `ip`, `at`. Helper `audit(actor, action, obj, diff, request=None)`.
- Serwis `assign_reviewers(stage, per_submission=2)`:
  - bierze wszystkie Submission w statusie LOCKED (najnowsze wersje) dla etapu;
  - pula: CommitteeMember ACTIVE w grupie reviewer; dla `stage.kind == DISTRICT` wyklucza recenzentów z `district == participant.district`;
  - przydziela 2 różnych recenzentów z najmniejszą bieżącą liczbą przydziałów (równoważenie), tworzy `Review(round=1, status=ASSIGNED)`, Submission → IN_REVIEW; idempotentny (nie dubluje przydziałów). Za mało recenzentów → `DomainError("NOT_ENOUGH_REVIEWERS", 409)`.
- Serwis `submit_review(review, score, comment_internal, comment_for_participant, annotations)`:
  - `score ∉ allowed_values()` → `DomainError("SCORE_NOT_IN_SCALE", 400)`; Review już SUBMITTED → 409 `REVIEW_ALREADY_SUBMITTED`; Submission nie IN_REVIEW/MODERATION → 409.
  - po zapisie: jeśli wszystkie Review rundy 1 są SUBMITTED: równe → `FinalGrade(CONSENSUS)`, Submission → GRADED_PROVISIONAL; różne → Submission → MODERATION.
  - `select_for_update` na Submission, aby dwa równoczesne zapisy nie utworzyły dwóch FinalGrade.
- Serwis `resolve_moderation(submission, actor, score, method, rationale)`: dozwolone dla koordynatora (method=MODERATION) lub trzeciego recenzenta z Review(round=2) (method=THIRD_REVIEW); tworzy FinalGrade, Submission → GRADED_PROVISIONAL, wpis AuditLog. Serwis `assign_third_reviewer(submission, reviewer)` – recenzent inny niż z rundy 1 i bez konfliktu okręgu.
- Rozszerzenie `Submission.objects.for_user(user)`: recenzent → Submission, do których ma Review; endpoint download z T-04 ma to respektować (plik tylko gdy `av_status == CLEAN`).
- API (prefiks `/api/grading/`):
  - `GET reviews/` – moje przydziały (IsActiveReviewer): submission id, `participant_public_code` (NIGDY imię/nazwisko/e-mail/szkoła), problem, status, download URL.
  - `GET reviews/{id}/`, `PATCH reviews/{id}/` (zapis DRAFT: adnotacje/komentarze/score bez walidacji finalnej), `POST reviews/{id}/submit/`.
  - W rundzie 1 recenzent nie widzi cudzych Review (serializer nie ujawnia; test).
  - `POST stages/{id}/assign/` (IsCoordinator) → liczba przydziałów.
  - `GET moderation/` (IsCoordinator) – Submission w MODERATION z obiema ocenami; `POST moderation/{submission_id}/resolve/` {score, rationale}; `POST moderation/{submission_id}/assign-third/` {reviewer_id}.
- Admin dla Review, FinalGrade, AuditLog (tylko odczyt dla AuditLog).

## Wymaganie z długu technicznego T-02 (obowiązkowe w tym tasku)
> **Nieaktualne od v0.11.x.** Organizator rozstrzygnął: „województwo nie ma znaczenia w przypadku
> członków komitetu, może być opcjonalne”. `district_verified` nie bramkuje już przydziału –
> konfliktem jest wyłącznie województwo **równe** województwu uczestnika na etapie wojewódzkim,
> a członek bez województwa ocenia prace ze wszystkich województw. Reszta poniższego opisu
> (kod zaproszenia z województwem, `verify-district`, audyt) obowiązuje.

`district` członka komitetu jest dziś samodeklarowany przy rejestracji, a reguła konfliktu interesów na nim polega. Dodaj:
- `InvitationCode.district` (nullable) ustalany przez koordynatora przy generowaniu kodu (`create_invitation(..., district=...)`, `manage.py create_invitation --district ...`).
- Przy `register_committee` z kodem mającym `district`: pole z payloadu jest ignorowane, profil dostaje `district` z kodu i `district_verified=True` (nowe pole `CommitteeMember.district_verified`, default False). Kod bez `district` → `district_verified=False`.
- `assign_reviewers` traktuje recenzenta z `district_verified=False` na etapie DISTRICT jako konfliktowego dla WSZYSTKICH okręgów (nie jest przydzielany), dopóki koordynator nie potwierdzi okręgu (`POST committee/{id}/verify-district/` {district} → IsCoordinator, ustawia `district_verified=True`, AuditLog).
- Testy: kod z okręgiem nadpisuje payload; niezweryfikowany recenzent nie dostaje przydziałów na DISTRICT, dostaje na ELIM/FINAL.

## Kryteria akceptacji (każde = test)
1. `assign_reviewers` daje każdemu LOCKED Submission dokładnie 2 różnych recenzentów; ponowne wywołanie nie dodaje nowych.
2. Na etapie DISTRICT recenzent z okręgu uczestnika nie jest przydzielany; jeśli po wykluczeniu zostaje < 2 → `NOT_ENOUGH_REVIEWERS`.
3. `GET reviews/` zwraca tylko własne przydziały; odpowiedź nie zawiera `first_name`, `last_name`, `email`, `school`.
4. Recenzent PENDING → 403; uczestnik → 403.
5. `score=3` przy skali {0,2,5,6} → 400 `SCORE_NOT_IN_SCALE`.
6. Dwie zgodne oceny → FinalGrade(CONSENSUS, score), Submission GRADED_PROVISIONAL; różne → MODERATION, brak FinalGrade.
7. Trzeci recenzent (runda 2) → FinalGrade(THIRD_REVIEW); koordynator → FinalGrade(MODERATION) + AuditLog.
8. Recenzent nie może pobrać pliku Submission, do którego nie ma Review (404); może pobrać przydzielony (302/200).
9. Recenzent A nie widzi score recenzenta B przed zakończeniem rundy 1.
10. Ponowny `submit` → 409.
