# T-04: Upload rozwiązań z egzekwowaniem deadline'u

## Kontekst
Repo `backend/`. Istnieją `apps.accounts` (User/Participant/uprawnienia) i `apps.competitions` (Edition/Stage/Problem/StageEntry/ScoringScale). Konwencje jak w `docs/tasks/T-02.md`. Referencja: `docs/PROJEKT.md` 1.3 i 2.2. Storage: MinIO (S3 API) w compose, ustawienia `S3_*` w `config/settings/base.py`; ClamAV w compose (`CLAMAV_HOST/PORT`).

## Zakres
Nowa aplikacja `apps.submissions`:
- Modele `Submission` i `SubmissionFile` jak w PROJEKT.md 2.2 (statusy: SUBMITTED, SCANNING, REJECTED_INFECTED, LOCKED, IN_REVIEW, MODERATION, GRADED_PROVISIONAL, APPEALED, FINAL). `unique_together (entry, problem, version)`. Manager `Submission.objects.for_user(user)`: uczestnik → własne; koordynator → wszystkie; recenzent → puste (przydziały dojdą w T-05).
- `apps/submissions/storage.py`: klasa `SubmissionStorage` z metodami `put(key, fileobj, content_type)`, `presigned_get_url(key, ttl)`, `open(key)`; implementacja S3 (boto3) + implementacja `LocalSubmissionStorage` (katalog `MEDIA_ROOT/submissions`) używana w testach (wybór przez ustawienie `SUBMISSION_STORAGE_BACKEND`). Klucz obiektu: `{edition_id}/{stage_id}/{participant_uuid_or_public_code}/{submission_uuid}/{sha256}.{ext}` – nigdy z nazwy pliku użytkownika.
- `apps/submissions/validators.py`: `validate_upload(upload, allowed_formats, max_file_mb) -> (ext, mime)`:
  - rozmiar > max → `DomainError("FILE_TOO_LARGE", 400)`;
  - PDF: pierwsze bajty `%PDF-`; ipynb: poprawny JSON, `nbformat.validate`, suma długości outputów ≤ 2 MB; py: UTF-8, brak bajtów NUL, ≤ 1 MB; inaczej `DomainError("INVALID_FILE_TYPE", 400)`. Rozszerzenie i `content_type` z żądania są tylko wskazówką, decyduje treść.
- Serwis `create_submission(user, stage, problem_number, upload) -> Submission`:
  - `entry = StageEntry.objects.select_for_update().get(participant__user=user, stage=stage)` w `transaction.atomic()`; brak → `DomainError("NOT_REGISTERED", 403)`; status DISQUALIFIED → 403.
  - `now = timezone.now()`; `now < stage.opens_at` → 403 `STAGE_NOT_OPEN`; `now > stage.submission_deadline` → 403 `DEADLINE_PASSED`.
  - `version = (max poprzednich) + 1` liczone wewnątrz blokady; sha256 liczony strumieniowo; zapis do storage; `SubmissionFile(av_status=PENDING)`; po commicie (`transaction.on_commit`) kolejkowanie `scan_submission_file.delay(file_id)`.
- Celery task `scan_submission_file(file_id)`: łączy się z clamd (protokół INSTREAM przez socket TCP, własna mała implementacja bez dodatkowych zależności, timeout 60 s), ustawia `av_status` CLEAN/INFECTED i status Submission (INFECTED → REJECTED_INFECTED). Gdy ClamAV niedostępny → retry (max 5, backoff) i log ostrzeżenia; w testach klient clamd mockowany.
- Serwis `close_stage(stage)`: dla każdej pary (entry, problem) najnowsza wersja ze statusem SUBMITTED → LOCKED; starsze wersje zostają jako historia. Idempotentny. Celery beat task `close_due_stages` uruchamiany co minutę: znajduje etapy z `submission_deadline < now` i bez flagi `closed_at` (dodaj pole `closed_at` do Stage migracją w competitions), wywołuje `close_stage`, ustawia `closed_at`.
- API (prefiks `/api/`):
  - `POST stages/{stage_id}/problems/{number}/submissions/` multipart `file` → 201 `{id, version, status, file: {original_name, size_bytes, sha256, av_status}}`. Permission `IsParticipant`, throttle scope `upload`. `entry` wyłącznie z `request.user`.
  - `GET me/submissions/` → lista własnych (najnowsza wersja per problem + historia).
  - `GET submissions/{id}/download/` → 302 na presigned URL (lub bezpośrednie wysłanie pliku w backendzie lokalnym); tylko właściciel lub koordynator; recenzent dojdzie w T-05. Plik z `av_status != CLEAN` może pobrać tylko właściciel.
- Admin: Submission z inline SubmissionFile (tylko odczyt).

## Kryteria akceptacji (każde = test; użyj freezegun do czasu)
1. POST poprawnego PDF w oknie → 201, Submission(version=1, SUBMITTED), SubmissionFile(PENDING), task skanu zakolejkowany (w testach CELERY eager z mockiem clamd → CLEAN po wykonaniu).
2. Drugi POST → version=2; obie wersje w bazie.
3. POST o `deadline_at + grace_seconds + 1s` → 403 `DEADLINE_PASSED`; o `deadline_at + grace_seconds - 1s` → 201.
4. POST przed `opens_at` → 403 `STAGE_NOT_OPEN`.
5. Plik `.pdf` z nagłówkiem `PK\x03\x04` → 400 `INVALID_FILE_TYPE`; plik większy niż `max_file_mb` → 400 `FILE_TOO_LARGE`.
6. `.ipynb` poprawny → 201 (gdy w allowed_formats); `.ipynb` z outputami > 2 MB → 400; `.ipynb` gdy allowed_formats == ["pdf"] → 400 `FORMAT_NOT_ALLOWED`.
7. Uczestnik bez StageEntry → 403 `NOT_REGISTERED`; uczestnik A nie może pobrać submission uczestnika B (404, nie 403 – nie ujawniamy istnienia); body z obcym `entry_id` jest ignorowane.
8. Współbieżność: dwa wywołania `create_submission` z dwóch wątków (używając `transaction.atomic` + prawdziwej bazy testowej Postgres, `pytest.mark.django_db(transaction=True)`) dają wersje 1 i 2 bez IntegrityError.
9. `close_stage` blokuje tylko najnowszą wersję; wywołany dwukrotnie nie zmienia nic więcej; `close_due_stages` pomija etapy przed deadline.
10. Klucz obiektu w storage nie zawiera oryginalnej nazwy pliku (`../../evil.pdf` w nazwie nie wpływa na ścieżkę).
