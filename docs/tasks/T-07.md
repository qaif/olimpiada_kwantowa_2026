# T-07: Wyniki, kwalifikacja do kolejnego etapu, publikacja (RODO)

## Kontekst
Repo `backend/`. Istnieją accounts, competitions, submissions, grading, appeals. Referencja: `docs/PROJEKT.md` 2.2 (QualificationRule, ResultsPublication) i 2.4 (publikacja).

## Zakres
W `apps.competitions` (lub nowej `apps.results`):
- Serwis `compute_stage_results(stage) -> list[dict]`: dla każdego StageEntry sumuje `FinalGrade.score` po najnowszej wersji Submission per Problem (brak Submission = 0). Wymaga, by każda oceniana Submission była FINAL; jeśli istnieje jakakolwiek w stanie IN_REVIEW/MODERATION/GRADED_PROVISIONAL/APPEALED → `DomainError("STAGE_NOT_FINALIZED", 409)`. Zapisuje `StageEntry.total_points`.
- Serwis `apply_qualification(stage)`: wg `QualificationRule.mode`:
  - MIN_POINTS: total >= min_points;
  - TOP_N: N najlepszych (remisy na granicy: wszyscy z tym samym wynikiem wchodzą);
  - TOP_N_PER_DISTRICT: N najlepszych w każdym okręgu (remisy jw.);
  - HYBRID: MIN_POINTS AND TOP_N.
  - Ustawia `StageEntry.status` QUALIFIED/NOT_QUALIFIED (DISQUALIFIED nietknięte) i tworzy `StageEntry(status=QUALIFIED→REGISTERED)` w następnym etapie tej edycji (ELIM→DISTRICT→FINAL), idempotentnie.
- `ResultsPublication`: OneToOne Stage, `published_at`, `snapshot` JSON, `anonymization` CODE/INITIALS_SCHOOL/FULL, `published_by`.
- Serwis `publish_results(stage, actor, anonymization)`: wywołuje compute + qualification, buduje snapshot: lista wierszy `{rank, display, district, points_per_problem: {1: 6, 2: 2, ...}, total, qualified}` gdzie `display` zależy od anonimizacji: CODE → `public_code`; INITIALS_SCHOOL → "J.K., XIV LO Warszawa"; FULL → imię i nazwisko tylko gdy `participant.publish_full_name`, inaczej `public_code`. Snapshot NIGDY nie zawiera e-maila, roku urodzenia ani id użytkownika. Ustawia `stage.results_published_at`. Ponowna publikacja nadpisuje snapshot (z AuditLog).
- API:
  - `GET public/results/{stage_id}/` AllowAny → snapshot (404 jeśli nieopublikowane). Dane wyłącznie ze snapshotu, nie z live query (test: zmiana FinalGrade po publikacji nie zmienia odpowiedzi).
  - `GET me/results/` (IsParticipant) → własne wyniki per etap z punktami per zadanie, komentarzami dla uczestnika i publicznymi adnotacjami; dostępne po `results_published_at`.
  - `POST stages/{id}/publish/` (IsCoordinator) {anonymization} → 201; `POST stages/{id}/compute/` → podgląd tabeli bez publikacji (IsCoordinator, pełne dane).

## Kryteria akceptacji (każde = test)
1. compute: suma po najnowszych wersjach; brak Submission = 0; niezakończona ocena → 409 `STAGE_NOT_FINALIZED`.
2. MIN_POINTS, TOP_N (z remisem na granicy), TOP_N_PER_DISTRICT, HYBRID – po jednym teście z tabelą oczekiwanych statusów.
3. Kwalifikacja tworzy StageEntry w następnym etapie tylko dla QUALIFIED; dwukrotne wywołanie nie duplikuje.
4. Snapshot CODE nie zawiera imienia, nazwiska, e-maila; FULL zawiera nazwisko tylko przy `publish_full_name=True`.
5. Publiczny endpoint bez logowania → 200; przed publikacją → 404; po zmianie FinalGrade odpowiedź niezmieniona.
6. `me/results/` przed publikacją → **200 z pustą listą** (endpoint jest listą własnych wyników; etap bez publikacji po prostu do niej nie wchodzi, a 404/403 sugerowałoby brak uprawnień). Po publikacji → punkty, `comment_for_participant`, tylko adnotacje `public=True`, bez `comment_internal`.
7. Uczestnik wywołujący `publish` → 403.

## Decyzje po przeglądzie (iteracja poprawkowa)
Każda ma test regresyjny w `backend/apps/results/tests/`; opis reguły w `docs/PROJEKT.md` 2.4.

1. **`FULL` tylko dla laureatów finału.** `publish_results` odrzuca `FULL` poza `StageKind.FINAL`
   (`400 ANONYMIZATION_NOT_ALLOWED_FOR_STAGE`, bez zapisu). W finale nazwisko wymaga trzech rzeczy
   naraz: `qualified`, `publish_full_name` oraz `guardian_consent` albo pełnoletności liczonej
   konserwatywnie z samego roku urodzenia (`ADULT_AGE = 19`). Inaczej wiersz dostaje `public_code`.
2. **Zero punktów nie kwalifikuje** w `TOP_N`, `TOP_N_PER_DISTRICT` i `HYBRID`. Próg (`_top_n_cutoff`)
   jest liczony wyłącznie z sum dodatnich, więc jest dodatni albo nie istnieje.
3. **Kwalifikacja jest odwracalna.** Spadek na `NOT_QUALIFIED` kasuje pusty wpis `REGISTERED`
   w następnym etapie; wpis z `Submission` zostaje i wraca jako `next_stage_conflicts`
   (pseudonimy). Audyt dostaje liczniki `created_entries` / `removed_entries` /
   `next_stage_conflicts`.
4. **Brama czasowa.** `apply_qualification` i `publish_results` przed `appeal_window_closes_at` →
   `409 APPEAL_WINDOW_OPEN`. `compute` (podgląd koordynatora) działa zawsze.
5. **Tabela publiczna zamrożona, wynik własny na żywo.** `me/results/` sumuje bieżące `FinalGrade`
   i dokłada `published_total` (z `ResultsPublication.entry_totals`) oraz `differs_from_published`.
6. **Brak `FinalGrade` blokuje przeliczenie** niezależnie od statusu zgłoszenia (także `FINAL`) –
   nieoceniona praca to brakująca ocena, a nie zero punktów.
7. **k-anonimowość i minimalizacja w snapshocie.** `INITIALS_SCHOOL` wymaga co najmniej trzech
   uczestników danej szkoły w etapie (`MIN_SCHOOL_GROUP`), inaczej wiersz spada do `public_code`.
   `district` trafia do snapshotu tylko w trybie `CODE`.
8. **Detale.** Jawny serializer adnotacji (`page`, `rect`, `text`), wpisy następnego etapu przez
   `bulk_create(ignore_conflicts=True)` (stała liczba zapytań), `select_for_update` na etapie
   w obu serwisach, `ResultsPublication.stage` na `on_delete=PROTECT` (migracja `0002`).
