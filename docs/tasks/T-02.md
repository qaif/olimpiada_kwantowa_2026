# T-02: Konta i RBAC

## Kontekst
Repo: `backend/` (Django 5.1, DRF, drf-spectacular). Konwencje: `apps/<app>/{models,services,api,urls,permissions,admin}.py`, testy w `apps/<app>/tests/test_*.py`, błędy domenowe przez `apps.core.api.DomainError(detail, code, status_code)` → odpowiedź `{"code": ..., "detail": ...}`. Czas zawsze `django.utils.timezone.now()`. Bez surowego SQL.

## Zakres
Nowa aplikacja `apps.accounts`:
- Custom `User` (`AUTH_USER_MODEL = "accounts.User"`, e-mail jako login, `USERNAME_FIELD = "email"`).
- Grupy (tworzone migracją danych): `participant`, `reviewer`, `appeals`, `coordinator`.
- `Participant` (OneToOne User): `public_code` (unikalny, 8 znaków, generowany losowo, np. `OLM-XXXXXX`), `school`, `district`, `birth_year`, `gdpr_consent_at`, `guardian_consent`, `publish_full_name` (default False).
- `CommitteeMember` (OneToOne User): `district` (nullable), `status` PENDING/ACTIVE/SUSPENDED, `is_appeals_committee`.
- `InvitationCode`: `code_hash` (sha256 kodu, unikalny), `created_by`, `expires_at`, `max_uses`, `used_count`, `grants_status` (ACTIVE|PENDING), `is_appeals` (bool). Serwis `create_invitation(created_by, ...) -> (obj, plain_code)` i `redeem_invitation(plain_code) -> InvitationCode` z blokadą `select_for_update` i inkrementacją `used_count`.
- Endpointy (prefiks `/api/auth/`):
  - `POST register/participant/` {email, password, first_name, last_name, school, district, birth_year, gdpr_consent: true, guardian_consent: bool} → 201 {id, email, public_code}; throttle scope `register`; bez `gdpr_consent=true` → 400 `GDPR_CONSENT_REQUIRED`.
  - `POST register/committee/` {email, password, first_name, last_name, invitation_code, district?} → 201 {id, email, status}; zły/wygasły/zużyty kod → 400 `INVALID_INVITATION`.
  - `POST login/` {email, password} → 200 {token} (DRF authtoken) + sesja; `POST logout/`.
  - `GET me/` → {id, email, roles: [...], participant: {...}|null, committee: {...}|null}.
  - `GET committee/pending/` i `POST committee/{id}/approve/` — tylko koordynator; approve ustawia ACTIVE i dodaje do grupy `reviewer` (+ `appeals` jeśli `is_appeals_committee`).
- Uprawnienia w `apps/accounts/permissions.py`: `IsParticipant`, `IsActiveReviewer` (grupa reviewer AND CommitteeMember.status == ACTIVE), `IsAppealsCommittee`, `IsCoordinator`. Recenzent PENDING → 403 na endpointach wymagających `IsActiveReviewer`.
- `manage.py create_invitation --email <koordynator> [--pending] [--appeals]` wypisuje kod.
- Admin dla wszystkich modeli (kod zaproszenia niewidoczny, tylko hash).

## Kryteria akceptacji (każde = test)
1. Rejestracja uczestnika tworzy User w grupie `participant` i Participant z unikalnym `public_code`.
2. Rejestracja uczestnika bez zgody RODO → 400 `GDPR_CONSENT_REQUIRED`.
3. Rejestracja komitetu z ważnym kodem `grants_status=ACTIVE` → CommitteeMember ACTIVE w grupie `reviewer`; z kodem PENDING → status PENDING, bez grupy `reviewer`.
4. Kod wygasły / zużyty (`used_count == max_uses`) / nieistniejący → 400 `INVALID_INVITATION`, `used_count` nie rośnie.
5. Koordynator zatwierdza PENDING → ACTIVE; uczestnik wywołujący approve → 403.
6. Endpoint testowy chroniony `IsActiveReviewer` (może być w testach przez `APIRequestFactory`) zwraca 403 dla PENDING i 200 dla ACTIVE.
7. `GET me/` zwraca role i profil; niezalogowany → 401.
8. Login zwraca token; token działa w nagłówku `Authorization: Token ...`.
